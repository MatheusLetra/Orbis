# M20 — Hardening, observabilidade e deploy

## Objetivo

Preparar o Orbis para produção sem alterar os contratos funcionais de M11–M19 e sem alterar Attachments.

## Releases por localização

Releases não armazenam artefatos. `artifactLocation` é uma string opaca, trimada, não vazia e limitada a 2048 caracteres. Pode representar URL, caminho, URI ou qualquer valor definido pelo usuário.

O backend não faz fetch, download, HEAD, checksum, MIME inspection, resolução de caminho ou validação externa. Não existe endpoint de download binário. Releases DRAFT podem não possuir localização; Releases PUBLISHED sem localização são rejeitadas. Publicação é update condicional por `DRAFT`, com um único vencedor concorrente e `409 CONFLICT` para republicação. Exclusão remove somente os dados da Release.

A implementação histórica de armazenamento físico, variáveis de caminho, filesystem, S3 e tabela BYTEA de Releases não faz parte do estado atual. Attachments permanecem inalterados em `attachments` + `attachment_blobs`.

## Backup e restore

O backup é PostgreSQL lógico em formato custom, incluindo schema, dados e BYTEA de Attachments. Artefatos de Releases não fazem parte do backup porque nunca são armazenados pelo Orbis. O restore deve ocorrer em banco isolado, validar migrations, contagens, checksums de Attachments, localizações de Releases e smoke de login/listagem/download de Attachments.

Política aprovada: RPO de 24 horas, RTO de 4 horas, backup diário e retenção técnica de sete backups diários. Credenciais e arquivos de backup devem permanecer fora do Git e com permissões restritas.
